# Decisions log

Decisions already made in the brief are in `docs/BRIEF.md` section 3. This file records decisions made while implementing.

## 2026-11-04 — M0/M1
- Development container has Node 22 (target laptop has Node 26). Code targets `node >=22`; nothing relies on Node 26 only features. Feature probes in `doctor` report what the running Node supports.
- CLI commands live in `src/cli/<name>.js` and are lazily imported by `bin/zerollm.js`.
- GGUF reader uses a buffered file cursor (never reads the whole file); uint64 values are returned as `Number` when safe, `BigInt` otherwise.
- `Q8_1` block size is 36 bytes (f16 d + f16 s + 32 int8), not 40; derived from ggml's `block_q8_1`.

## 2026-11-04 — M2/M3
- Pre-tokenizer regexes spell out contractions with explicit case classes (`'[sS]`, `'[rR][eE]`, ...) instead of `(?i:...)`. Equivalent, and works on every Node (the Node 22 dev container lacks inline modifiers; `doctor` still reports the probe).
- Special tokens (GGUF token_type 3 control and 4 user-defined) are matched literally in text only when `special: true`. Chat templates encode scaffolding with special parsing ON and message content with it OFF, so user text such as `<|im_end|>` cannot inject control tokens.
- Control tokens are hidden when decoding for display (`skipControl`), user-defined ones (e.g. `<think>`) are shown.
- Qwen3 chat defaults to **non-thinking** (pre-filled empty `<think></think>` block) because thinking would burn tokens at ~2-5 tok/s; `--think` enables it. This differs from the model's own default.
- Llama 3.1/3.2 system header ("Cutting Knowledge Date...") uses a fixed date string by default so prompts are deterministic.
- Reference path uses a Q8_0-style activation quantization with **f32** scales (as in the brief); ggml itself uses f16 scales, so logits differ very slightly from llama.cpp.
- Reference kernels support F32/F16/BF16/Q8_0/Q4_0 only; K-quants arrive in M8.
- Tests use an independent naive whole-sequence forward pass (`test/naive-forward.js`, double precision, no KV cache) as the oracle for the optimized-style reference path. Mutation-checked: GQA mapping, attention scale, RoPE on K, QK-norm, SiLU, causal range and residual mistakes are all caught.

## 2026-11-04 — M4
- `generate()` is an async generator that yields to the event loop after every token **including during prefill**, so Ctrl+C is responsive even on long prompts (setImmediate cost is negligible vs ~0.5 s/token). It also reuses the longest common prefix between `model.tokens` and the new prompt (multi-turn chat only prefills the new turn), and always recomputes the last prompt token to obtain logits.
- Sampler order: penalties (in place, restored afterwards) -> top-k (O(V log k) heap) -> temperature softmax -> min-p -> top-p -> sample. `--temp 0` is plain argmax (after penalties).
- Stop strings are matched on the decoded text stream with hold-back of partial matches (`StopFilter`); the matched text is never printed.
- In `chat`, readline owns Ctrl+C (raw mode), so the REPL listens to `rl.on('SIGINT')`; `run` uses `process.on('SIGINT')`. Second Ctrl+C force-exits (130).
- `--threads` is accepted but ignored (with a warning) until M5.

## 2026-11-04 — M5 (worker pool)
- **Partitioning:** every weight matrix is split by output rows (multiples of 4, last worker takes the remainder); attention is split by head (`floor(w*count/n)` ranges). Each worker stores only its slices, in its own private `WebAssembly.Memory` (64-byte-aligned offsets) so M6's SIMD kernels can address them directly and the 4 GB wasm32 limit applies per worker.
- **Per layer, 6 barriers:** (A) q/k/v row slices -> shared; (B) per-KV-head k-norm + RoPE + write K/V cache; (C) per-query-head q-norm + RoPE + attention; (D) o-proj + residual on own rows; (E) gate/up row slices -> SwiGLU slice; (F) down-proj + residual on own rows. Plus one after the embedding lookup. Norms and activation quantization are recomputed redundantly by every worker (cheaper than a barrier). ~170 barriers/token for a 28-layer model.
- **No postMessage per token:** the main thread issues a command through a shared `Int32Array` (`Atomics.add` + `notify`) and awaits completion with `Atomics.waitAsync`, so the event loop (SIGINT etc.) stays live. The KV cache lives in one `SharedArrayBuffer` (layout `[layer][k|v][pos][kvDim]`), written by the worker that owns that KV head.
- **Bit-exactness:** workers use the same kernel functions as the reference path and every output row/head is computed by exactly one worker with identical arithmetic, so logits are *bit-identical* to the single-thread reference regardless of worker count. Tests assert exact equality (not tolerance). This is only true while the JS kernels are used; the WASM kernels (M6) will need tolerance-based parity tests.
- **Head-aligned q/k/v row splits were rejected:** with 8 KV heads over 6 workers (2,2,1,1,1,1) the busiest worker would carry 25% of the qkv work instead of 16.7%. Even row splits plus one extra barrier balance better.
- **Process lifetime:** workers are `unref()`'d (a forgotten `close()` must not hang the process) -- but `unref()` must be called *after* attaching the `'message'` listener, because adding the listener re-refs the port (found by test: unref-before-listener hung the process). The pool therefore holds its own keep-alive interval while loading and during each `forward()`.
- **Failure handling:** a worker that throws posts an error and the pool terminates all workers (others would otherwise wait forever at a barrier); `forward()` polls with a 200 ms `waitAsync` timeout, so an externally killed worker rejects the call instead of hanging.
- `--threads N`: default = logical processors / 2 (physical-core guess); `--threads 1` uses the single-thread reference path (kept as the oracle). `zerollm bench` compares thread counts and verifies identical greedy output.
- `node --test` runs every `.js` file in a directory named `test`; worker fixtures live in `test-fixtures/` for that reason.

## 2026-11-04 — M6 (WASM SIMD kernels)
- **Own binary emitter** (`src/compute/wasm/builder.js`): LEB128, sections, typed locals, structured control flow with label handles, plain + 0xFD SIMD opcode tables. Every opcode in the tables used by kernels is verified numerically against a JS model (`test/wasm-builder.test.js`), including the exhaustive f16->f32 sequence over all finite half values.
- **Kernel design** (`kernels.js`, generated by a JS program): `matvec_q8_0` / `matvec_q4_0`, 4 rows per group (+1-row remainder loop), the activation chunks are widened (`i16x8.extend_*`) once per block and reused by all 4 rows, `i32x4.dot_i16x8_s` for the int8 dot, f32x4 accumulators scaled by `d_w * d_x`, horizontal sum once per row. Weight pointers use `v128.load` with memarg offsets (+2, +18) because blocks are 34/18 bytes (unaligned loads are fine on x86).
- **f16 scale conversion** is done arithmetically in the kernel: `f32.reinterpret(((h & 0x7fff) << 13) | ((h & 0x8000) << 16)) * 2^112` (handles denormals and sign; verified for all finite f16). A 256 KB lookup table was rejected (cache pressure).
- **Memory layout per worker:** `[weight slices][xq int8][xd f32 scales][y f32]` in the same private `WebAssembly.Memory`; the module imports it as `env.mem`. The JS side quantizes the activation straight into the scratch region, the kernel writes results to the scratch `y`, and JS copies them to the shared output slice.
- **Numerics:** SIMD results differ from the JS reference only by float summation order (~1e-7 relative on tiny models). On a *random-weight* 0.6B-shaped model the final logits can differ by several percent, because a 1e-7 change can flip an int8 activation rounding and a random network amplifies it. Verified NOT to be a kernel bug: perturbing the reference's own norm weights by 1e-7 relative gives exactly the same divergence (5.3e-2 / 6.9e-2 / 8.7e-2 at 2/3/4 layers), the integer parts are exact, and `kernels=js` in the pool stays bit-identical to the reference. Consequences: parity tests for SIMD use a relative tolerance + argmax checks on tiny (well-conditioned) models; `bench` will report that greedy output differs between js and wasm only as information. Real-model output must be checked by hand (REAL-MODEL-CHECK.md).
- The SIMD result itself is bit-identical for any worker count (row grouping does not change per-row arithmetic).
- `--kernels auto|wasm|js` (auto = wasm when SIMD validates). `--threads 1 --kernels js` is the untouched single-thread reference path. F32/F16/BF16 matrices keep using the JS kernels inside a SIMD pool.
- `close()` now shuts workers down gracefully (exit command, 2 s grace) before terminating, so they can flush output (used by the opt-in `ZEROLLM_PROFILE=1` per-token profile of worker 0).

## 2026-11-04 — M7 (batched prefill, prefix cache)
- **Batched kernels** `mm_q8_0` / `mm_q4_0`: tiles of 2 weight rows x 4 tokens (+ remainder tiles), weights widened to int16 once per tile, activations stored pre-widened as int16 (`xq16`, token t at element offset `t*cols`). All float operations happen in the same order as in `matvec_*`, so batched results are **bit-identical** to token-by-token results (asserted for every tile shape and, at the model level, for every split point of a prompt into batches, with both SIMD and JS kernels).
- **One SPMD pass handles B tokens** (B = 1 is ordinary decoding with the single-vector kernel): the barrier count per pass is unchanged, so barrier cost is amortized over B tokens. Shared activation buffers are `[B][dim]`; `CTRL.TOKENS` carries the token ids; the last token of the batch is the only one that gets logits. Positions inside a batch are causal (K/V of the whole batch are written before attention runs).
- `maxBatch` default 16 (`--batch N`, hard cap 64). `generate()` prefills in chunks of `model.maxBatch` through `prefillTokens()`, which yields to the event loop between passes (Ctrl+C stays responsive).
- **Prefix cache** (`src/model/prefix-cache.js`): file = magic + header JSON (model fingerprint = name|size|mtime|kernel flavour, layer count, kvDim, exact token list) + raw f32 K/V of the first n positions per layer. Key = sha1(fingerprint + token ids), so a hit is the state a fresh prefill would produce. Any mismatch, truncation or damage returns "miss" instead of throwing and leaves the model untouched. Written via tmp file + rename; keeps the 16 newest files. Default directory `<model dir>/.zerollm-cache` (models/ is gitignored); `--cache-dir`, `--no-cache`. Only the system-prompt prefix is cached (template scaffolding + system message), and only when it is >= 32 tokens. Kernel flavour is part of the key because SIMD and JS states differ at rounding level.
- Known follow-ups (profile-driven): attention is plain JS and becomes the dominant prefill cost for long prompts; activation quantization is redundant per worker.

## 2026-11-04 — M8 (Q5_0 + K-quants)
- **Layouts verified against an independent implementation**, not memory: `tools/gen-quant-vectors.py` runs the official `gguf-py` dequantizers on random + extreme blocks (odd f16 scales, all-0xFF, all-zero) and writes `test/data/quant-vectors.json` (125 KB); `test/quant-vectors.test.js` checks our dequantizers against it (mutation-tested: a flipped nibble order, wrong high-bit plane, wrong Q6_K scale index, off-by-one Q5_0 high bit or wrong 6-bit scale packing each fail). The python tool is dev tooling only (`pip install gguf numpy`), nothing in the runtime depends on it.
- **Supported tensor types:** F32, F16, BF16, Q4_0, Q5_0, Q8_0, Q4_K, Q5_K, Q6_K. Other types fail early with a clear message listing what is supported (`assertSupportedTensorTypes`), and `info` marks them. Q4_1/Q5_1/Q2_K/Q3_K/IQ* are not implemented.
- **Dot-product formulation:** activations stay Q8_0-style (int8 + f32 scale per 32). Every K-quant sub-block is 32 wide (Q6_K groups 16), so each maps onto one activation block: Q4_K/Q5_K `d*sc*sum(q*xq) - dmin*mn*sum(xq)`, Q6_K `d*scale*sum((q-32)*xq)`, Q5_0 `d*sum((q5-16)*xq)`, times the activation scale. (llama.cpp uses Q8_K 256-wide activations; ours is a slightly finer-grained, equally valid scheme.)
- **No repack yet:** kernels read the ggml block layout in place (Q5_0's high-bit plane is expanded with `i8x16.swizzle` + `i8x16.eq`; Q4_K/Q5_K unpack the 6-bit scales with three i32 loads and mask/shift tricks; Q6_K assembles 6-bit values with and/shift/or). Repacking at load time is a possible M9 optimization.
- **Batched prefill for these types** falls back to the single-vector kernel once per token (correct, bit-identical to token-by-token, but the weights are re-read per token). Only Q8_0 and Q4_0 have tile (matmul) kernels so far.
- **Model-level test tolerance for SIMD vs reference:** random-weight tiny models showed occasional ~0.4-0.6% logit differences between the SIMD pool and the reference. Verified to be the same int8-activation rounding-flip effect as in M6: 6 of 40 random 1e-7 weight perturbations of the *reference itself* produce a flip divergence up to 3.7e-3, identical in size to the SIMD difference (3.68e-3), and in one case perturbation and SIMD give the exact same value (4.42e-3). The tests therefore assert: JS pool bit-exact; SIMD within 2% of the top logit with cosine > 0.9999, argmax equal wherever the top1-top2 margin exceeds 3x the observed difference, and at least N-3 of N positions within 1e-3; kernel-level tests (1e-4 of rms) catch real kernel bugs.
- `tools/random-blocks.js` generates random raw blocks with sane f16 scales (zero-centred weights) for synthetic K-quant models (`makeTinyModel({quant: 'q4_k_m' | 'q5_k' | 'q6_k' | 'q4_k' | 'q5_0'})`; K-quants need rows that are multiples of 256, otherwise the tensor falls back to F32 like ggml does).

## 2026-11-04 — faster K-quants and SIMD attention (M9a)
- **K-quant batched kernels** (`mm_q5_0/q4_k/q5_k/q6_k`): 2 rows x 4 tokens tiles, weights widened to int16 once per tile, int16-widened activations, float operations in exactly the decode kernels' order => bit-identical to decode kernels (tested for 8 row/block/token shapes per format). The Q4_K/Q5_K min correction no longer needs per-sub-block activation sums inside the kernel: `quantizeAct` also emits the integer block sums (`xs`), so `mins += (dmin*mn*dx)*xs` is three scalar operations.
- **What actually limits K-quant speed** (tools/kbench.mjs, weights cache-resident): the kernels are compute-bound, 3-5x slower per weight than Q8_0 (Q4_K ~5.4, Q5_K ~4.4, Q6_K ~2.6 vs Q8_0 ~12 Gw/s/thread in the VM), so batching alone cannot help (it only removes weight re-reads). Experiment: `i16x8.extmul` + pairwise-add dot (no widening) is 25-35% faster for Q4_K/Q5_K *decode* but 20-50% slower in the batched tiles (V8/x64 turns an extmul into several instructions; the tile form amortizes widening over 4 tokens), so decode and batched kernels deliberately use different dot forms. Further K-quant speedups (vectorizing the 8 per-super-block scale/min conversions, fusing Q6_K groups) are listed as future work.
- **Attention ownership by KV head** (instead of by query head): worker w owns KV heads `splitRange(nHeadKv, n, w)` and all query heads of those groups. K/V never cross workers, so the cache is private, lives in the worker's wasm memory (layout per layer `[k|v][owned head][pos][headDim]`), needs no barrier between the K/V write and attention, and can be read by SIMD kernels. Cost: with 8 KV heads over 6 workers the busiest worker does 2/8 of the attention work (vs 1/6 ideal) and with more workers than KV heads some workers have no attention work; acceptable now that attention is ~10% of the token. `attn_scores` / `attn_av` handle one head (head_dim must be a multiple of 16, otherwise the JS path is used); softmax stays JS (`Math.exp`), so SIMD attention differs from the reference only in f32 vs f64 accumulation. `--kernels js` keeps the original arithmetic over the private cache and is still bit-identical to the reference.
- **Prefix cache with private KV:** export/import are worker commands (`CMD_KV_EXPORT/IMPORT`) through a shared `kvStage` buffer, `PoolModel.kvGet/kvSet(layer, isV, n)`; `PrefixCache.save/load` became async. File format unchanged (f32).

## 2026-11-04 — M9 engine side: f16 KV cache, RAM estimates, 8B-shaped test
- **`--kv f16`** stores the per-worker KV cache as IEEE half floats (written with round-to-nearest-even in JS, read by dedicated SIMD kernels `attn_scores_f16` / `attn_av_f16` that convert 8 halves to f32 with the same arithmetic trick as the weight scales, `((h&0x7fff)<<13 | (h&0x8000)<<16) * 2^112`, vectorized). Default stays f32. Cost: the f16 attention kernels do more ALU work per cached value (conversion); benefit: half the KV memory, which is what matters on a RAM-tight machine. Prefix-cache files stay f32 (workers convert on export/import); the cache key includes the KV precision.
- **What f16 costs in accuracy:** differences between f16 and f32 caches are at the int8-activation-quantization noise floor of the engine. Experiment on a tiny random model: perturbing the *reference's own weights* by only 1e-5 relative already changes the final logits by ~1% (median 9.5e-3), and 5e-4 (about one f16 rounding step) gives 1.2e-2, the same as f16 vs f32 KV (1.0-1.4e-2 at every position). The strong correctness checks are SIMD-vs-JS agreement of the f16 path (2e-7 on the tiny model) and the exact f16 export/import round trip.
- **RAM estimator** (`estimateRam`): weights + KV (`ctx` x bytes per token for the chosen precision) + per-worker scratch + runtime (250 MB + 40 MB per worker), and the busiest worker's WebAssembly memory (weights/threads + its KV heads) against the 4 GB wasm32 limit (hard error with advice). `info` prints both KV precisions side by side; `run`/`chat`/`bench` warn when the estimate exceeds 90% of free RAM and say whether `--kv f16` would fix it.
- **Measured vs estimated** (8B-shaped synthetic Q4_K_M-style file, 8.19B parameters, 5.43 GB on disk, linux): peak RSS 5.27 GiB with a 65-token context; the estimator predicts weights 4.71 GiB + runtime ~0.4 GiB + KV 0.02 GiB = ~5.1 GiB. KV pages are only resident once touched, so RSS grows by 295 KB (f32) / 147 KB (f16) per context token for this shape: at ctx 2048 the estimator's totals are 6.15 GB (f32 KV) and 5.86 GB (f16 KV), under the brief's 9 GB bound with room to spare.
- `tools/gguf-writer.js` gained `writeGGUF` (streams to disk) and `makeTinyModel({outFile})`, which made generating the 5 GB test file possible without doubling memory.

## 2026-11-04 — K-quant decode dot form is selectable (`ZEROLLM_KDOT=extmul|wide`)
First measurement of the kernel/attention work on the target laptop (Ryzen 5 7530U): tests pass, kbench shows the K-quant kernels ~1.7x faster than in the dev VM (Q4_K decode 9.4 Gw/s/thread), prefill of Qwen3-4B Q4_K_M improved 5.96 -> 8.23 tok/s, but decode went 5.77 -> 4.4-4.8 tok/s. The only decode-path change that could plausibly be CPU-dependent is the integer dot form of the Q4_K/Q5_K/Q6_K decode kernels (`i16x8.extmul` + pairwise adds, 25-35% faster in the VM, vs the older widen + `dot_i16x8_s`). Both forms are now built from the same generator (`buildKernelModule({kdot})`, env `ZEROLLM_KDOT` read per worker), both are tested against the JS reference and the whole suite passes under either, and `kbench` prints them side by side so the default can be chosen from data on the target CPU instead of from the VM. Profile data from the user's machine (`ZEROLLM_PROFILE=1`) is the other missing piece: in the VM an 8B-shaped model spends 81% of a token in kernels, 15% in barrier waits, 2% in activation quantization.

## 2026-11-04 — Llama 3 review before the first real Llama file
- **`ignore_merges` for the Llama 3 pre-tokenizer kind:** the HF Llama 3 tokenizer (`"ignore_merges": true`) uses a whole pre-token directly when the vocabulary contains it instead of running merges; its merge list was derived from tiktoken ranks and does not always reproduce every vocabulary entry. Qwen2 does not do this. Implemented (`Tokenizer.ignoreMerges`, default true for kind `llama3`), tested with a vocabulary that contains tokens no merge produces.

- **`--show-prompt`** on `run` / `chat` prints the token count, ids and decoded text (control tokens visible) of the prompt actually fed to the model, the first thing to check when output looks wrong.

## 2026-11-04 — App foundations (A0/A1)
- **Library entry `src/index.js`** (`loadModel`, `Engine.generate` as an async generator of text, `inspectModel`, `loadTokenizer` for exact prompt token counts without weights, RAM gate throwing `EngineMemoryError`). The CLI keeps its own code path; the app only uses this surface.
- **Local server hardening** (the page is served from 127.0.0.1, so every web page in the same browser can reach it): 127.0.0.1 bind, exact Host check (DNS rebinding), Origin check, per-launch random token (header `X-Token`; `?t=` only for the event stream), token removed from the address bar after load, CSP `default-src 'self'`, no dotfiles / traversal in static serving, 25 MB body cap. Tested with forged Host/Origin headers over raw sockets.
- **One resident model, one generation at a time** (`EngineHost`, `busy` error for a second send); the model is loaded with `kv: f16` to halve KV memory (measured on 0.6B Q8_0 at 3000 tokens: peak RSS 1485 MiB f32 vs 1158 MiB f16).
- **Window:** Edge/Chrome in `--app` mode if found (Windows), else the default browser; the process exits ~20 s after the last page connection closes. Single-instance via `app.lock` (pid, port, token) that is verified by pinging the old instance.
- **Markdown safety:** raw HTML in model output is shown as text, only http(s)/mailto links, no images; marked 18 and highlight.js 11 are vendored unmodified with their licenses (copied from Skibeti37's static folder).
- **Context meter** uses the exact token count (tokenizer + template, no weights loaded) and is capped to the model's trained context.
- **UI check tool:** `tools/ui-smoke.mjs` drives the page with a globally installed Playwright (dev only, not a dependency) and writes screenshots.

## 2026-11-04 — System prompt cached on disk in the app
- The app's system prompt (+ template header) is ~200 tokens on a real tokenizer, which is ~30 s of prefill on an 8B model at ~7 tok/s, paid again after every app start. `Engine.primePrefix(ids, {dir})` restores the KV state of those tokens from `<data>/cache/*.kv` (or reads them once and saves them); it only acts on a freshly loaded model, later messages already reuse the live state.
- **What is cached:** `stablePrefixIds` = common token prefix of the prompts for a Norwegian, an English and an unrecognised user message, so the language reminder (which differs per message and sits last in the system message) never invalidates the cached part; the app verifies that this prefix really is a prefix of the final prompt and otherwise skips caching. Cache key = model file identity + kernel flavour + KV precision + exact token ids; files are f32 (~260 KB/token for an 8B model, so ~50 MB), at most 16 are kept.
- Not measured on the laptop yet: expected effect is that the first message after a restart skips most of the "Leser teksten..." wait (only the user's own text is read); the very first run after a model/context change still pays once. The `done:` line in app.log shows `system prompt cache: hit|saved`.

## 2026-11-04 — Embedding model (nomic-embed-text v1.5) in the engine and the app
- **What runs:** architecture `nomic-bert` only (the model Skibeti37 uses, so vectors are interchangeable): token + token-type-0 embedding -> LayerNorm; per layer post-norm: fused QKV (no biases) -> RoPE split-half base 1000 -> bidirectional attention -> out proj -> +x -> LayerNorm -> SwiGLU -> +x -> LayerNorm; mean pooling over all tokens ([CLS]/[SEP] included), not normalised (llama.cpp returns the unnormalised mean, Skibeti37 stores that). WordPiece tokenizer reads the GGUF `bert` vocabulary (word-initial pieces carry `▁`, continuation pieces do not), HF-uncased normalisation (NFD, lower-case, accents removed, punctuation/CJK split).
- **Written from llama.cpp's graph from memory, NOT yet verified against a real nomic file** (none could be downloaded in the dev VM). The oracle for the fast path is our own reference encoder (`src/embed/ref-encoder.js`; fast path vs reference cosine > 0.9995 for f32/Q8_0/Q4_K_M+Q6_K synthetic models, bit-identical across worker counts). The ground-truth check for the real thing is `zerollm embed <model> --compare documents/<skibeti37 doc>.json`: Skibeti37's stored llama.cpp vectors vs ours for the same chunk text (expect > 0.99). It also tries "accents kept" vs "stripped", because I am not sure which one llama.cpp's WPM tokenizer does (matters for å).
- **Fast path:** data parallelism instead of the decoder's SPMD barriers: every worker holds a full copy of the weights (~90 MB) and embeds whole sequences with the batched SIMD kernels (all tokens of a sequence = one batch) and the SIMD attention kernels; LayerNorm/RoPE/softmax in JS. Measured on the 4-vCPU dev VM with a synthetic nomic-shaped Q4_K_M model: ~30 tok/s per worker (10 s per 300-token chunk per worker, 86 % in the K-quant matmul kernels - the same compute-bound kernels as LLM prefill), 59 tok/s with 2 workers. Expect roughly 1 chunk/s with 6 workers on the laptop (unmeasured).
- **App:** documents get vectors in the background after they are added (temporary pool of <= 4 workers, freed afterwards); questions are embedded by one resident worker released after 10 idle minutes; ranking = reciprocal-rank fusion of BM25 and cosine, falling back to BM25 alone for chunks/models without vectors. No `search_document:` / `search_query:` prefixes, like Skibeti37 (interchangeable vectors; nomic recommends them, an option for later). Documents created here now carry vectors, so Skibeti37 can search them too (when indexed).
- **Not done:** multilingual embedding models (nomic-embed-text is mostly English; e5/bge-m3 would be better for Norwegian but need an XLM-R/SentencePiece tokenizer), relaxed-SIMD int8 dot for faster matmuls.

## 2026-11-04 — Indexing locks chat and models
Adding a document with a search model installed starts indexing at once (the lock is set synchronously inside `add_document`, so nothing can slip in between). While it runs the server refuses `send_message`, `continue_message`, `summarize_document`, `delete_model`, `unload_model`, context/thread changes, KV changes and resets with the error `indexing`, and the page greys out the composer, attach and `/` buttons and the model picker and shows a progress banner (it also survives a page reload: `state().indexing`). Reason: the encoder uses every core (up to 8 workers) and a chat model generating at the same time would make both crawl. A document added while a reply is being written (or while another one is indexed) is queued and indexed right after; installing the search model (download finished) indexes all documents without vectors. Indexing itself does not touch the chat model, which stays loaded.

## 2026-11-04 — Documents: relevance without word lists, XML-style prompt block
Reported: "hei" with a document attached answered with a copy of the excerpts. Causes: (1) the fallback inserted the document's opening chunks whenever nothing matched, even for a greeting; (2) the `[From file]` block was easy for a small model to echo. Fix: **no excerpts unless something actually matches** (BM25 score > 0, or cosine >= 0.55 when vectors exist; the 0.55 is a number taken from the self-test pairs, not a word list) and the block is now `<documents><document name="...">...</document></documents>` + `Question: ...` with a short instruction. Deliberately **no word lists** (no greeting list, no "summarize"-style trigger words, and the old stop-word list is gone): BM25's IDF already makes words that occur in most chunks worthless in any language. Language-specific rules that remain: the suffix stemmer (morphology, not words). Consequence: a question like "what is this about" matches by whatever words it shares with the text, or nothing; that is accepted.

## 2026-11-05 — Why "Leser teksten..." came back on every answer, and the fix
The model keeps what it has read (KV cache) only for an UNCHANGED prompt prefix. My prompt changed early text between turns, so most of the conversation was read again each time: (1) a language reminder at the end of the system message, chosen per message from a hard-coded word list, flipped between turns (measured on the tiny model: turn 2 re-read 385 of 602 tokens, all of the history); (2) a math hint chosen by a regex of words did the same; (3) document excerpts were put into the last user message only, so on the next turn that message looked different and everything after it was read again. Native llama.cpp (Skibeti37) had the same design but reads several times faster, so nobody noticed. Fix: **the prompt only ever grows at the end.** The system prompt is constant (the language rule is one fixed sentence; both word-list heuristics are gone); document context is stored WITH the user message it was retrieved for (`context`, an extra field in the chat file that Skibeti37 ignores) and rendered in front of that message for the rest of the conversation; chunks already somewhere earlier in the conversation are not added again; regenerate/continue reuse the stored context. Costs: each document question permanently adds its excerpts (up to ~1500 tokens) to the conversation, which the rolling summary folds away when the window fills; slash-command text still sits in the system prompt, so a turn that uses a command re-reads (accepted). Regression tests (`test/app/append-only.test.js`) assert turn N+1's prompt starts with all of turn N's prompt, for any language and content.
- Math: single-dollar math now renders in the two shapes models write it (`$ x $` with spaces inside, `$x^2$` tight with a TeX/operator character); `$5 og $10` stays money.
